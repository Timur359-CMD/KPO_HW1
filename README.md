# ВышКат — учёт парка кикшеринга

Домашнее задание №1 по «Конструированию программного обеспечения» (ВШЭ): доменная модель и консольное
приложение учёта парка. Техника попадает в парк только после техосмотра, на баланс ставятся транспорт и вещи,
у каждого объекта есть инвентарный номер, есть отчёты по числу единиц и суммарной энергии и список техники для новичков.

Стек: Java 21, Maven, Google Guice (DI-контейнер), JUnit 5, Mockito.

## Запуск

1. Установить JDK 21 и IntelliJ IDEA.
2. `File → Open`, выбрать `pom.xml`, *Open as Project*, дождаться загрузки Maven.
3. Запустить класс `ru.hse.vyshkat.Main` (зелёный треугольник рядом с `main`). Ввод вводится в окне *Run*.

Тесты: правый клик по `src/test/java` → *Run 'All Tests'* (или `mvn test`).


## Как пользоваться

Меню:

| Пункт | Действие |
|---|---|
| 1 | Принять транспорт: выбрать вид, ввести название, простоту (1–10), износ (%), расход энергии; затем техосмотр |
| 2 | Поставить вещь на баланс (шлем, зарядный шкаф) |
| 3 | Загрузить данные из CSV-файла |
| 4 | Отчёт: число единиц по видам и суммарное суточное потребление энергии |
| 5 | Список техники, которую можно выдавать новичкам |
| 6 | Названия и инвентарные номера всей техники и вещей |
| 0 | Выход |

**Формат файла** (`sample-data/fleet.csv`): пять полей через `;` — `ВИД;название;простота;износ;расход_энергии`.
Виды транспорта: `SCOOTER`, `BICYCLE`, `ELECTRIC_BICYCLE`; вещи: `HELMET`, `CHARGING_CABINET`
(простота и износ пустые). Строки с `#` и пустые пропускаются. Ошибочные строки не прерывают загрузку:
программа сообщает номер строки и причину.

## Демонстрационный сценарий

Данные для демонстрации лежат в файле, а не в коде. Запустить `Main` и выполнить:

1. `3`, затем `sample-data/fleet.csv`: принято 5 единиц транспорта, самокат с износом 60% **отклонён техосмотром**,
   три строки с ошибками показаны с номерами строк, поставлены на баланс 2 шлема и зарядный шкаф
   («Обработано строк: 12, успешно: 8»).
2. `4`: «Всего единиц на балансе: 8», «Суммарное суточное потребление энергии: 5.60 кВт·ч».
3. `5`: техника для новичков: 3 единицы (Segway не подходит по простоте, Haibike по износу).
4. `6`: инвентарные номера `VK-0001`…`VK-0008` у техники и вещей вместе.
5. `1` → вид 2 → простота 7 → износ 60: техосмотр отклоняет велосипед, номер не выдаётся.
6. Ошибки ввода (`9` в выборе вида, `abc` вместо числа, несуществующий файл) показывают сообщение, программа продолжает работу.

## Архитектура

```
ru.hse.vyshkat
├── domain    Inventoriable, EnergyConsumer, InventoryItem
│             Transport ─ Scooter, Bicycle ─ ElectricBicycle
│             Equipment ─ Helmet, ChargingCabinet
│             TransportKind, EquipmentKind (виды для меню и загрузки)
├── service   ServiceCenter ← StandardServiceCenter       техосмотр
│             InventoryNumberGenerator ← Sequential…      инвентарные номера
│             NoviceRule ← DefaultNoviceRule              правило для новичков
│             Fleet, ReportService, FleetLoader, InspectionResult
├── di        AppModule                                    корень композиции Guice
└── app       ConsoleApp                                   ввод и вывод, без логики парка
```

## Логика решений

- **Инвентарный номер выдаётся при постановке на баланс**, а не при создании объекта. Отклонённая техника номера не получает
  и номера не «сгорают» (`FleetTest.rejectedTransportNeitherEntersFleetNorGetsNumber`).
- **Транспорт и вещи — разные ветки** (`Transport` и `Equipment`). `Fleet.acceptTransport` принимает только транспорт,
  `registerEquipment` только вещи, поэтому транспорт нельзя поставить на баланс в обход техосмотра.
- **Энергия — свойство интерфейса `EnergyConsumer`**, а не базового класса: у обычного велосипеда и шлема её нет.
  Суммарная энергия считается по всем объектам парка (транспорт и вещи), которые этот интерфейс реализуют.
- **Техосмотр** (`ServiceCenter`) смотрит на износ: выше порога (30%, настраивается в `AppModule`) техника отклоняется с причиной.
- **Правило для новичков** (`DefaultNoviceRule`): простота ≥ 6 **и** износ ≤ 20%. Базовое правило задания усложнено: слишком изношенную технику новичкам не выдаём.
- **Интерфейс отделён от логики.** `ConsoleApp` только вводит и выводит. Разбор файла находится в `FleetLoader` (работает со списком строк, поэтому тестируется без файлов и консоли),
  правила находятся в `service`. Чтение самого файла делает интерфейс.
- **Данные для демонстрации не зашиты в код**: они в `sample-data/fleet.csv`; в коде приложения примеров нет, только в тестах.

## SOLID и DI

- **S (единственная ответственность).** `Fleet` отвечает за баланс, `ReportService` за отчёты, `FleetLoader` за разбор файла,
  `StandardServiceCenter` за правила осмотра, `ConsoleApp` за ввод и вывод.
- **O (открытость и закрытость).** Новый вид транспорта: класс-наследник `Transport` и одна константа в `TransportKind`;
  `Fleet`, `ReportService`, `FleetLoader` и меню не меняются (меню и загрузчик строятся по `TransportKind.values()`).
  Другое правило для новичков или другой техосмотр: новая реализация `NoviceRule` или `ServiceCenter`.
- **L (подстановка Лисков).** `ElectricBicycle` — это `Bicycle` с расходом энергии, и везде, где ждут `Bicycle` или `Transport`,
  работает любой потомок (`DomainTest.electricBicycleIsStillABicycle`, `ReportServiceTest`).
- **I (разделение интерфейсов).** Вместо одного большого интерфейса три маленьких понятия: инвентарный номер (`Inventoriable`),
  потребление энергии (`EnergyConsumer`) и простота для новичка (поле `Transport`). Велосипед и шлем не обязаны реализовывать «потребление энергии».
- **D (инверсия зависимостей).** `Fleet` зависит от интерфейсов `ServiceCenter` и `InventoryNumberGenerator`, `ReportService` от `NoviceRule`.
  Реализации связываются только в `AppModule` (Guice). Поэтому в тестах техосмотр подменяется без правки боевого кода.

**Что сознательно не сделано (против overengineering).** Нет интерфейсов у `Fleet`, `ReportService`, `FleetLoader`, `ConsoleApp`:
по одной реализации и нет причины подменять. Нет репозиториев, фабрик фабрик и слоя DTO.
Интерфейс заведён только там, где есть причина:
- `ServiceCenter`: требуется заданием и подменяется в тестах;
- `InventoryNumberGenerator`: чтобы в тестах номера были предсказуемыми, а `Fleet` не считал номера сам;
- `NoviceRule`: задание прямо допускает усложнять правило;
- `Inventoriable` и `EnergyConsumer`: общее поведение разнородных объектов (транспорт и вещи).

## Ответы на обязательные вопросы

**1. Какой принцип применён наиболее явно?** Инверсия зависимостей (D). `service/Fleet.java` получает в конструкторе
`ServiceCenter` и `InventoryNumberGenerator`, а не конкретные классы; связывание в `di/AppModule.java`.
Подмена техосмотра в тестах не требует ни одной правки в `Fleet`.

**2. Какой принцип сознательно ограничен?** Открытость и закрытость (O). Чтобы новый вид транспорта появился в меню и в загрузке из файла,
нужно добавить константу в `TransportKind` (или `EquipmentKind`): это единственное место правки существующего кода.
Автоматическое обнаружение видов через рефлексию или `ServiceLoader` убрало бы эту правку, но добавило бы «магии»
для проекта такого размера, поэтому явный перечень приемлемее. Вторая осознанная уступка: `ConsoleApp` совмещает меню, ввод и форматирование;
выделять отдельные классы для ввода и печати при таком объёме значит добавлять классы без выгоды (SRP на уровне пакетов соблюдён: логика парка в `service`).
Третья: аннотации `@Inject` стоят в классах `service`, то есть слой знает о Guice; альтернатива (`@Provides` на каждый класс) только добавила бы шума.

**3. Что сломается при расширении?**
- *Новый вид транспорта* (например, гироскутер): ничего не сломается, нужен класс-наследник `Transport` и константа в `TransportKind`;
  меню, загрузка из файла, отчёты и техосмотр подхватят его сами (`DomainTest.kindsCreateMatchingObjects`).
- *Сотрудник:* не сломается. Он не `Inventoriable` и не наследует `Transport` или `Equipment`, поэтому `Fleet` его не примет
  (на баланс сотрудники не ставятся, как требует задание). Учёт сотрудников будет отдельным сервисом.
- *Склад запчастей:* штучные запчасти подходят как наследник `Equipment` (`SparePart`) и константа в `EquipmentKind`; номера и отчёты заработают сразу.
  Сломается модель только при учёте количеством («100 болтов одной позицией»): у `Equipment` у каждой единицы свой номер,
  для количественного учёта нужен отдельный сервис склада.
- *Мой вариант расширения:* станция аренды как `RentalStation extends Equipment implements EnergyConsumer`: попадёт в инвентарный список
  и в суммарную энергию без правок `ReportService`.

**4. Какой тест фиксирует решение техосмотра и правило «для новичков»; как подменяется зависимость?**
- Решение техосмотра: `FleetTest.rejectedTransportNeitherEntersFleetNorGetsNumber` и `acceptedTransportGetsNumberAndEntersFleet`.
  `ServiceCenter` подменяется mock-объектом Mockito (`@Mock`, передаётся в конструктор `Fleet`). В `FleetTest.fakeServiceCenterCanBeALambda`
  подмена выполнена fake-лямбдой (интерфейс `ServiceCenter` с единственным методом).
- Подмена через DI-контейнер: `AppModuleTest.serviceCenterIsReplacedByMockThroughContainer`: `Modules.override` заменяет привязку `ServiceCenter`
  в настоящем `AppModule`, а `Fleet` из контейнера использует mock.
- Границы порога износа: `StandardServiceCenterTest.decisionDependsOnWearThreshold` (износ 30% принимается, 31% отклоняется).
- Правило для новичков: `DefaultNoviceRuleTest.boundaries` (простота 5 и 6, износ 20 и 21).

## Роль ИИ
В ходе реализации проекта применялись инструменты искусственного интеллекта. На этапе инициации ИИ использовался для первоначального планирования и структурирования задач. В процессе разработки нейросеть выступала в роли ассистента и редактора кода, помогая оптимизировать алгоритмы и повышать наглядность программных решений. Кроме того, около половины всех тестов были спроектированы и успешно реализованы под непосредственным руководством ИИ. На финальном этапе инструменты искусственного интеллекта использовались для глубокой редактуры, стилистической коррекции и финального оформления итогового отчета на основе предоставленного мной черновика
